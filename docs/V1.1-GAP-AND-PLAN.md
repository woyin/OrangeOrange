# v1.1 差距、执行顺序与验收

本文保留开工时盘点和实施顺序。下表“没有”描述当时状态，不代表当前实现。当前逐项追踪以 [208 条需求证据](V1.1-REQUIREMENTS-EVIDENCE.json)、[运行证据](P0-VERIFICATION.md)及根目录 IMPLEMENTATION_STATUS.md 为准。

基线：`Home_Durable_Agent_v1.1/SRS.md` 及三份专项设计。原布局保留，不重写稳定的 Pi/任务底座。当前源码与测试是事实来源，旧状态标签仅作线索。

## 假设与范围

按规格的发布段推进：先完成 M0–M5 P0；M6 Browser Worker、M7 Bot/Routine 是独立 P1 里程碑，P2 为可选，不用它们冒充 P0 功能，也不从总体追踪删除。目标设备暂按4核/4GiB/SSD，现有开发机不是目标设备。没有账户或源备份时先实现生产路径及明确版本的夹具，不把夹具通过等同实账号/源版本验收。

## 顺序和职责

1. 主流程完成M0核对与追踪。检查：`npx vitest run tests/pi-adapter.test.ts tests/recovery.test.ts tests/control-crash.test.ts tests/control-policy.test.ts`，已22项通过。
2. 三个互不重叠模块并行：`src/migrations`、`src/connectors`、`src/execution`；各自编写契约、夹具及故障回归。主流程独占`src/control`、公共运行时接入、OpenAPI与根文档，避免并发写冲突。
3. 后端公共接口确定后接入认证HTTP、Pi工具和Web三个新P0页面。检查：真实HTTP流程、Playwright桌面/390px、旧模块回归。
4. 审计备份、秘密、OAuth回调、恢复、导入中断、未知副作用。检查：MT/GM故障用例和空环境恢复。
5. 执行完整构建/本地/容器门禁；需求逐条对应代码、测试、实测范围。实账号/设备/长期运行未获得证据时保持未验收。

技术选择：保留现有`src/control`模块边界，以ControlStore实体容纳新领域，避免新增数据库和跨库事务。外部历史只读归档；续聊使用新的Pi会话，不向Pi私有表写入外部checkpoint。Gmail真实发送仅在明确动作批准后发生，本次开发授权本身不是发信授权。
